# Roadbook Web 数据库分库分表与建表规范

更新日期：2026-10-09。版本：V1.0。状态：后续数据库设计与迁移的准入规范；尚未建库、修改 Prisma 模型或执行迁移。

本规范适用于 Web 使用的 PostgreSQL。实体字段与业务语义见 [领域模型与数据库设计](领域模型与数据库设计.md)，事务与故障行为见 [一致性与故障处理设计](一致性与故障处理设计.md)。本文负责约束物理归属、命名、约束、分区、迁移和验收，不能替代这两份设计。

## 1. 基线决策与术语

首期采用**每个环境一个 Web 业务数据库，数据库内按 DDD 限界上下文分 schema，单主写入**。不按用户、手机号、会员档位或路线创建数据库，不提前做水平分片。生产、预览、开发必须隔离。

| 层级 | 本项目含义 | 首期规则 |
| --- | --- | --- |
| 实例/托管项目 | 计算、存储、连接与故障资源边界 | 生产使用独立资源边界；非生产不得挤占生产连接与容量 |
| database | 连接目标和本地事务边界 | 一个环境一个 Web 业务库；预览可使用独立数据库或隔离分支 |
| schema | 同一数据库中的命名空间 | 按上下文划分；支持同库事务与跨 schema 外键 |
| table | 一个实体、关系、不可变版本或投影 | 明确唯一写入方、聚合归属和生命周期 |
| partition | 一张逻辑表的数据库内分区 | 初期不启用；需要查询与清理证据 |
| shard | 数据按键分布到不同数据库 | 初期不启用；需要路由、重分片及跨库一致性方案 |

PostgreSQL 的 schema 不等于独立数据库；普通连接不能把另一个数据库的表当成本库表直接关联。schema 的访问依赖权限配置，本身不提供独立故障或计算资源隔离。[PostgreSQL schema 说明](https://www.postgresql.org/docs/current/ddl-schemas.html)

分库分表不能自动满足 CAP。权威写入无法连接可信主节点时不确认成功；公共可重建投影允许有界旧数据。单主事务的约束保证与复制、故障切换的数据丢失风险分别验收。

## 2. 环境与数据库归属

| 环境 | 逻辑标识示例 | 数据与权限要求 |
| --- | --- | --- |
| 开发 | `roadbook_web_dev` | 合成或获准的脱敏样本；不得连接生产私人数据 |
| 预览 | `roadbook_web_preview_<preview_id>` | 每个预览独立数据库/分支，或专用非生产库中的受控预览环境；不得仅靠表名前缀隔离生产数据 |
| 生产 | `roadbook_web_prod` | 私人 UGC、账户与业务权威数据；独立凭据、备份与恢复目标 |

以上为逻辑命名示例，实际数据库名由托管供应商限制决定。生产与非生产不能只靠一个连接 URL 的默认 schema 参数区分。预览如果共享非生产数据库，必须串行管理迁移、避免不同分支互相覆盖，且使用合成数据；需要验证互不兼容的迁移时必须创建独立数据库/分支。

现有库是否已有真实数据、服务依赖与独立资源尚未核实。实施前建立资源清单并确认旧应用的连接目标；不能直接把现有旧库认定为新的 Web 生产库，也不能静默复制旧用户数据。

Redis 与 PostgreSQL、对象存储分别配置环境隔离。Redis 不能保存唯一权威路线、手机号凭据、会员订阅、授权或预算账本；对象存储保存私有正文与权威几何载荷，PostgreSQL 保存归属、版本、引用与状态。

## 3. DDD schema 与完整表归属

新表保留领域前缀，物理全名采用 `schema.table`。前缀用于跨库日志、事件、迁移审查时识别归属；不能用前缀替代 schema 或访问权限。

| 上下文 | schema | 归属表；此列为物理表名，访问时加 schema |
| --- | --- | --- |
| 身份与访问 | `identity` | `identity_user`、`identity_external_identity`、`identity_auth_session`、`identity_data_grant`、`identity_phone_credential`、`identity_sms_challenge`、`identity_sms_delivery` |
| 会员权益 | `membership` | `membership_tier_version`、`membership_subscription`、`membership_entitlement_decision` |
| 私人路线 | `planning` | `planning_route_plan`、`planning_control_point`、`planning_route_revision`、`planning_import_receipt`、`planning_route_geometry`、`planning_geometry_segment`、`planning_geometry_chunk`、`planning_route_derivation`、`planning_derivation_range`、`planning_route_access_grant` |
| 路线导入 | `ingestion` | `route_import_asset`、`route_import_job`、`route_import_candidate` |
| 精选路线 | `featured` | `featured_user_marker`、`featured_route_version` |
| 外部事实 | `external_facts` | `external_data_source`、`external_fact_snapshot` |
| 路线计算 | `calculation` | `calculation_route_result` |
| 通用持久支撑机制 | `platform` | `platform_idempotency_record`、`platform_outbox_event`、`platform_consumer_receipt`、`platform_background_job` |
| UGC 治理 | `ugc` | `ugc_route_publication`、`ugc_dataset_version`、`ugc_dataset_item` |
| 知识检索 | `knowledge` | `knowledge_document_version`、`knowledge_chunk`、`knowledge_embedding_space`、`knowledge_embedding` |
| AI 辅助 | `ai` | `ai_run`、`ai_run_attempt`、`ai_tool_call`、`ai_route_proposal`、`ai_feedback`、`ai_usage_budget`、`ai_usage_reservation` |

示例：`planning.planning_route_plan.owner_id` 关联 `identity.identity_user.id`。用户关联使用稳定 UUID，手机号放在 `identity.identity_phone_credential`，不在路线表重复保存。

表归属清单共 46 张拟议逻辑表，**不是首期建表清单**。`featured_route_version` 仍可暂用静态文件；`knowledge_embedding` 的物理向量布局待模型维度确定。按 [推进阶段](Web数据架构与部署推进方案.md)启用所需 schema 和表，不为未上线能力创建空壳系统。

每张表只能由所属上下文的仓储负责业务写入。跨上下文应用用例可协调多个仓储参与同一事务；禁止一个领域直接绕过另一个领域的不变量。`platform` 只提供幂等、投递和任务能力，不拥有路线或账户业务规则。

旧六个 Prisma 模型保持现有映射与语义，作为遗留区管理；没有显式映射时通常位于 `public`，实际以迁移与库结构核验为准。新 Web 业务表不得继续随意加入 `public`；也不得为了符合新规则直接移动、删除或重命名旧表。

## 4. 物理拆库的准入与演进

| 情况 | 优先处理 | 允许拆出的范围 |
| --- | --- | --- |
| 普通查询慢、连接耗尽 | 查询计划、必要索引、分页、连接预算、池化与缓存 | 不能仅凭一次慢请求决定拆库 |
| 外部事实同步或算路投影持续争用资源 | 有界任务、批处理、读投影；测量 CPU、IO、锁等待与延迟 | 可重建事实快照或计算投影 |
| 向量索引构建显著影响业务写入 | 限速重建、容量调整，必要时独立检索存储 | 知识分块/向量投影；账户、授权权威仍在业务库 |
| 明确的数据驻留、独立恢复或安全隔离需求 | 先记录要求、访问边界与恢复目标 | 经评审的完整数据边界 |
| 单主写容量经优化仍不满足已确认目标 | 用代表性负载验证，比较升级与分片成本 | 经证明可路由的聚合分片；不预设用户数阈值 |

拆库前必须形成 ADR（架构决策记录），记录负责人、实测基线、目标、成本、替代方案、迁移/回退、恢复与验收证据。尚无生产规模与延迟目标，不设置“达到多少行自动分库”的虚假阈值。

下列原子提交首期必须留在同一数据库内：

1. 路线版本校验、聚合内容、修订、幂等结果与对应 outbox。
2. 导入候选确认、正式路线创建与确认回执；复制/fork/裁剪的源权限和版本核验、目标内容与血缘提交。
3. 必须在提交时成立的会员权益决策与路线变更；长任务按既定受理权益策略复核。
4. 手机号唯一绑定、验证码一次消费、用户/凭据关联与会话创建的相应用例。
5. AI 预算预留/核销与账本；AI 建议接受状态与新路线修订。

不是每次操作都修改上述所有表；事务只包含该用例必需的数据，不包含短信、对象上传、地图或模型网络调用。

如果未来把相关权威数据拆到不同数据库，普通 FK 和本地事务就不能继续提供跨库保证。必须先把协议改为明确的受理/完成状态、事件版本、幂等消费、补偿、对账与删除传播，再迁移；不能仅删除 FK 后继续宣称原子提交。跨库授权不能单凭长期缓存放行，未确认授权或撤销状态时停止受保护操作。

每个写库拥有自己的事务 outbox 和幂等记录，与该库业务变更一起提交；禁止把所有写库的 outbox 放进一个独立“消息库”后做无保障双写。拆出的投影可由本地消费者维护，但不能反过来成为路线与授权的事实来源。

## 5. 表、字段、约束与索引命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| schema | 小写英文下划线，固定上下文映射 | `external_facts` |
| 表 | 单数领域名，保留约定前缀 | `planning_route_revision` |
| 字段 | 小写英文下划线；表达业务含义 | `owner_id`、`distance_m`、`expires_at` |
| 主键约束 | `pk_<table>` | `pk_planning_route_plan` |
| 唯一约束/唯一索引 | `uq_<table>_<meaning>` | `uq_planning_route_revision_plan_version` |
| 外键约束 | `fk_<table>_<meaning>` | `fk_planning_route_plan_owner` |
| CHECK | `ck_<table>_<meaning>` | `ck_planning_control_point_position` |
| 普通索引 | `ix_<table>_<meaning>` | `ix_planning_route_plan_owner_updated` |
| Prisma 模型/属性 | 带领域含义的 PascalCase/camelCase，映射物理名称 | `PlanningRoutePlan` / `ownerId` |

项目统一把对象名限制在 63 个 ASCII 字节内；超过时缩短语义部分并加稳定短哈希，迁移中显式固定名称，禁止依赖数据库自动截断。禁止拼音、含糊的 `data/info/temp`、日期后缀业务表和 `user_123_route` 动态表。分区子表若后续获准，使用 `<parent>_pYYYYMM` 等可生成的维护名称，不能成为应用查询契约。

原生 SQL、迁移 SQL、运维脚本必须写明 `schema.table` 并参数化值。表名/schema 不得由用户输入拼接；允许的动态对象必须来自服务端固定清单。禁止依赖可被非信任主体创建对象的 `search_path`。

## 6. 建表结构与约束准入

### 6.1 字段与载荷

- 实体主键为服务端生成的 `uuid`；关联表允许有明确理由的复合主键，必须在表设计卡声明。UUID 不提供访问授权。
- 必填业务事实使用 `NOT NULL`；可空字段必须写出 NULL 含义。未知金额、未知调用结果不能默认写成零或成功。
- 业务时间使用 `timestamptz`，服务端 UTC；创建时间不可变，变更时间由受控写入路径维护。不是每张不可变明细表都需要 `updated_at`。
- 云端版本用有界校验的 `bigint`，API 防止 JavaScript 精度丢失；金额用定点 `numeric` 并保存币种，不用浮点金额。
- 坐标、单位、哈希、JSONB 与敏感字段遵循领域设计。JSONB 必须有结构版本、大小边界与服务端校验；核心外键、归属、状态、顺序和可检索事实不得藏在 JSON 中。
- 原始文件、链接快照、长文本和大几何载荷放私有对象存储；表中保存对象引用、哈希、大小、格式、归属和状态。正文读取前重新检查权限，不长期存储可公开访问的签名 URL。
- 不添加 `CHECK(position < 20)` 或固定 20 个点的数组列。点数是会员业务策略；所有档位另有可测试的技术上限，过期不截断已保存路线。

### 6.2 关系与不变量

| 不变量 | 必须落实的约束 |
| --- | --- |
| 用户与路线关联 | `owner_id` 引用稳定用户 PK；手机号码不是 FK，不随改号修改路线归属 |
| 同一方案的修订唯一 | 唯一 `(plan_id, version)`；有归属冗余时增加匹配的复合唯一键与 FK |
| 子对象不能串到其他用户/方案 | 冗余 `owner_id/plan_id` 必须通过相应复合 FK 绑定同一聚合；不只分别引用两个存在的 ID |
| 当前几何属于正确方案 | 当前几何引用匹配 `owner_id/plan_id/geometry_id`；同事务提交并处理循环依赖 |
| 控制点顺序 | `CHECK(position >= 0)`、唯一 `(plan_id, position)`；连续顺序由聚合用例校验，重排采用安全更新顺序或延迟约束 |
| 固定源版本派生 | 血缘固定源修订与范围；源删除不能级联删除其他用户的独立目标内容 |
| 有效手机号唯一 | 活跃凭据的号码检索摘要唯一、活跃用户绑定唯一；使用部分唯一索引，具体有效条件与解绑状态一致 |
| 幂等 | 唯一 `(actor_id, operation, key)`，同时比较请求哈希；系统执行者采用明确作用域，不能用 NULL 漏掉唯一性 |
| 预算与 nullable owner | 用户预算与系统预算分别定义部分唯一索引，不能依赖普通含 NULL 唯一键去重 |
| 权益与状态合法 | 档位版本不可变、合法状态有约束；跨行数量和转移条件用事务与并发控制，不用跨行 CHECK |

复合外键可空时必须明确“全部为空或全部有值”的语义，必要时使用 `MATCH FULL` 或等价 CHECK，避免部分 NULL 绕过关系。软删除记录不是“可以被任意引用”的授权证明；外键存在、状态许可和调用者权限分别检查。

删除规则必须逐条声明 `RESTRICT/NO ACTION/CASCADE/SET NULL` 及原因。仅完全附属于根、没有独立保留/血缘意义的明细可在物理清理时采用 CASCADE；账户、路线修订、对象引用和派生血缘禁止无审查的整链级联。用户注销先停止访问，再依治理流程清理、去标识或保留最小合法墓碑；备份恢复后重放删除记录。

### 6.3 索引与查询

每个列表提供分页上限和稳定排序；优先 keyset 游标，例如活跃路线按 `(owner_id, updated_at DESC, id DESC)`，游标同时包含时间与 ID。软删除过滤是否需要部分索引由实际查询确定。

每个 FK 必须评估引用侧索引；默认覆盖高频关联与父对象删除检查，避免和已有复合索引重复。PostgreSQL 不会因为声明 FK 自动创建引用侧索引。[官方约束说明](https://www.postgresql.org/docs/current/ddl-constraints.html)

唯一索引服务业务去重，普通索引服务查询；不得为“以后 AI 可能会用”给所有列建索引。大 JSONB 不默认建 GIN，经纬度普通 B-tree 不等于空间索引；PostGIS、pgvector 和 ANN 索引分别评审，未获安装授权不安装扩展。

新增索引必须记录目标查询、预估选择性、写入成本与查询计划验收。高频业务读取不得扫描完整修订、几何载荷或模型输出。

## 7. 分区与水平分片标准

初期保持普通表。日志型尝试、历史任务或事实快照只有在长期增长、时间范围查询/清理与实测维护成本吻合时，才评估时间分区；“大表”本身不是充分条件。

分区方案必须明确分区键、边界、未来分区创建、迟到数据、默认分区告警、保留期限、备份、恢复、FK 和唯一性。PostgreSQL 分区表的主键/唯一约束必须包含全部分区键；不能给幂等记录按月分区后，把原本全局唯一的操作键悄悄改为每月唯一。[官方分区限制](https://www.postgresql.org/docs/current/ddl-partitioning.html)

手机号有效绑定、路线修订唯一键、幂等键和预算窗口等全局不变量表默认不做时间分区。若分区收益确凿，先设计独立去重注册表或合适的分区键，并验证并发与清理不会丢失去重保证。

水平分片另立 ADR；必须覆盖聚合共置、稳定分片路由、热点用户、跨用户 fork、公共发布、跨分片预算、全局标识、迁移切换与对账。禁止简单用 `hash(user_id) % N` 后随意改变 N，也不能将手机号或会员等级作为可变路由键。未经这些验证不实施分片。

## 8. Prisma、连接与权限标准

当前 `packages/db` 使用 Prisma 7.8.0 和 PostgreSQL adapter，只有一个 datasource、迁移目录与运行连接入口；尚未声明 DDD schemas。本规范落地到代码时：

1. 同一业务数据库保持一条受控迁移历史，继续由 `packages/db/prisma/migrations` 管理。按已启用范围设置 datasource 的 `schemas`，模型/枚举用 `@@schema`，模型/字段用 `@@map/@map`；遗留模型显式保留真实归属。
2. Prisma 支持 PostgreSQL 多 schema 与跨 schema 关系，但移动已有模型归属可能生成删除/重建操作。必须审查生成 SQL；保留数据的搬迁需专门设计 SQL、对象依赖与回滚，不能只修改 `@@schema` 后部署。[Prisma 多 schema 文档](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/multi-schema)
3. Prisma 不能完整表达的约束、部分索引、延迟约束或扩展对象进入显式 SQL 迁移，并保留后续漂移检查规则。不能生成一次后在后续迁移中无意删除。
4. 只有真实拆成多个数据库后，才建立对应独立配置、生成客户端与迁移目录；禁止多个互不协调的迁移链同时管理同一库中的同一对象。
5. 运行与迁移连接分别配置；池化/直连按供应商能力核实，不假设连接变量名称即可保证直连。Vercel 多实例与部署重叠纳入总连接预算；进程单例不等于全局连接池。

角色至少区分：迁移角色（DDL）、应用运行角色（必要 DML）、只读运维角色。运行角色不得拥有 schema/table，不得拥有 CREATE/ALTER/DROP 权限；应用、浏览器和模型均不得取得迁移凭据。具体授权由受控迁移/运维步骤核验，包括未来对象的默认权限。

schema 所有权交由受控迁移角色，检查 `public` 的 CREATE 权限与 `search_path`，不将可被非信任主体写入的 schema 加入解析路径。单个应用运行角色访问多个 schema 时，DDD 写入边界仍需代码约束，不能宣称已实现模块级数据库权限隔离。需要硬隔离时再评审独立角色、连接与事务协作。

RLS 仅作为实际配置并验证后的纵深防御；使用连接池时必须证明事务级用户上下文不会泄漏到下一请求。不能以“用了 RLS”替代仓储归属过滤，也不能把有绕过权限的连接当作隔离证据。

## 9. 迁移与发布门禁

| 步骤 | 必需产物与检查 |
| --- | --- |
| 设计 | 表设计卡、上下文归属、事务清单、查询/索引、隐私/删除与容量预估 |
| 生成 | 在隔离开发环境生成迁移；人工审查 DDL、隐式删表、锁影响、默认值与回填 |
| 演练 | 隔离空库与有代表性旧结构样本各演练；核对数据数量、内容哈希、约束和旧应用兼容性 |
| 准备 | 明确备份/恢复点、RPO/RTO、执行人、观察窗口与失败处置；确认目标环境与连接权限 |
| 执行 | 用户明确授权后，受控步骤执行生产 `migrate:deploy`；禁止构建/请求启动时自动迁移 |
| 切换 | 扩展 → 有界回填 → 核验 → 切换读写 → 观察；保持旧应用版本的必要兼容窗口 |
| 收缩 | 另行评审删除旧列/表、收紧 NOT NULL 或停止旧协议；应用回滚不等于数据库回滚 |

生产禁止 `db push`、`migrate dev`、`migrate reset`、自动演示 seed 或手改后不留迁移记录。已应用迁移不可修改或删除；修复通过新迁移。回填有批次、游标、幂等和可暂停能力，不在一个长事务中处理全部路线。

新建大索引、扫描验证或回填前评估锁与资源成本；需要并发索引构建时确认它不能放进普通事务块，并与迁移工具的执行方式配套。扩展安装、数据库迁移执行、真实数据导入、部署、删数据和 push 都需要单独的明确授权；本文件不是执行授权。

## 10. 表设计卡模板与示例

每张拟新增表必须完成以下设计卡，不能只提交字段清单：

| 必填项 | 填写要求 |
| --- | --- |
| 身份 | 物理全名、Prisma 名称、上下文、负责人、启用阶段 |
| 职责 | 权威事实/版本/关系/投影，聚合根或明细，唯一业务写入方 |
| 字段 | 类型、长度/精度、单位、NULL 含义、默认值、敏感级别 |
| 约束 | PK、业务唯一、FK/复合归属、CHECK、删除行为、不可变规则 |
| 用例 | 创建/变更/删除路径、授权、版本、同事务表、幂等与 outbox |
| 查询 | 目标查询、分页/排序、索引与计划验收；避免全量读取 |
| 治理 | 来源、发布与 AI 用途授权、保留期限/待定负责人、删除与备份传播 |
| 容量 | 预计用户/行/增长/载荷、技术上限；未知项写待测，不编造数值 |
| 发布 | 兼容策略、回填、锁影响、恢复/失败处置、验收与观测 |

以 `planning.planning_route_plan` 为例：P3 启用，`PlanningRoutePlan` 是私人路线聚合根，权威正文由控制点或不可变几何表示；`owner_id` 引用身份 UUID，当前版本正整数、默认私有。保存命令按 owner 与基础版本条件更新，内容、修订、幂等回执、outbox 同事务提交；列表按 owner、更新时间、ID 分页。手机号与 AI 正文不写入此表；会员点数策略不写成 20 点 DDL 限制。删除先写墓碑并关闭访问，几何与修订依引用和保留政策清理。容量与保留期仍待 P0 确认，此示例不表示可以跳过完整字段、索引及删除设计直接建表。

## 11. 验收与实施顺序

1. **P0**：确认本规范，完成环境/旧库依赖清单、核心表设计卡、RPO/RTO、隐私与保留政策；决定首期账户与会员策略。
2. **P3**：在独立实施任务中修改多 schema 配置、核心模型与增量迁移；先验空库，再验旧结构样本和权限；不移动旧六表。
3. **P4**：按导入与派生阶段增建资产/候选/权威几何/授权/权益表，验证原子确认、来源删除、并发保存与高点数容量。
4. **P5–P6**：随事实、UGC 和 AI 功能启用新增表；向量布局、扩展与拆库分别决策。

实施验收至少证明：物理表与 schema 清单一致；约束真实存在；跨用户复合关系被数据库拒绝；并发同版本保存仅一次成功；验证码不可重复消费；有效手机号和幂等键不重复；会员放开点数无需改表；fork 目标不因源删除丢失；运行角色无法 DDL；迁移升级后兼容窗口有效；备份可恢复且删除记录可重放。

当前证据仅为仓库配置检查、官方能力核对与文档一致性验证。上述数据库、权限、并发、容量、恢复验收均尚未执行；不得将规范落盘表述为数据库已实施。
